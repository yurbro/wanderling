# 路途 App：整体开发框架与思路（v1）

日期：2026-10-04
状态：构思稿，待讨论后收敛

## 0. 一句话定位

路途是一个「放置式旅途陪伴」应用：一个小小的旅人替你走向山河湖海，走过真实世界的城市与风景；而他头顶的天空、天气和昼夜，与你此刻所在的现实世界同步。你不需要完成任何任务，打开就能看见他走到了哪里、那里的天气如何，偶尔会收到他寄来的明信片。

目标用户：生活与工作压力较大的年轻人。产品气质：治愈、低压、有一点点诗意。画风参考：旅行青蛙（旅かえる）。

## 1. 三个最底层的产品决策

### 1.1 旅人为什么会前进

这是整个产品最底层的决策，直接决定它像哪一类产品：

| 机制 | 参考产品 | 优点 | 风险 |
|---|---|---|---|
| 纯时间驱动（放置） | 旅行青蛙 | 零压力，不打开也在走 | 用户参与感弱 |
| 步数驱动 | Walkr、Pikmin Bloom | 「奔向山河湖海」变成字面意义，很动人 | 久坐的用户看着旅人停在原地会有负罪感，变成新压力 |
| 专注时间驱动 | Forest | 切合「工作压力」场景 | 把陪伴变成了工具 |

建议：时间驱动打底，现实行为温和加速。旅人永远在走（哪怕用户三天不打开），用户的步数或专注时段只是让他走得更远、看到更多。原则是「只有加分，没有扣分」：没有连续打卡、没有掉落、没有「你错过了什么」的焦虑文案。一个减压产品不能自己变成压力源。

### 1.2 「现实同步」到底同步什么

原始想法里有一个需要先理清的张力：背景要和用户的现实定位同步，但旅人又要走遍世界各地。直接合并会矛盾（用户在广州，旅人在冰岛，画面到底画哪）。

建议的解法是分层：天空归现实，大地归旅途。

- 天空层（昼夜、天气、季节、月相）同步用户所在地的现实：你那里下雨，他那里也下雨；你那里天黑了，他也点起灯。这是「同一片天空下」的陪伴感来源。
- 大地层（地形、建筑、地标、植被）跟随旅途进度：他此刻走到哪，就画哪里的风景。
- 定位的额外用法：旅程从用户所在城市出发，第一站就是「家」；用户现实中换了城市，旅人会知道；「回家」是一个有仪式感的事件。

这个分层同时就是技术架构中的渲染分层，见第 6 节。

### 1.3 画风：参考旅行青蛙

旅行青蛙的画风特点：手绘线条、低饱和暖色、大量留白、线条略带手抖感、几乎不用渐变和光效、物件少而精。对本项目有三个实际好处：资产制作成本低（一个景点一张卡片级插画即可）、与治愈低压的气质吻合、容易用程序做昼夜与天气的整体色调变化（整体套色，而不是重画）。

需要注意的差异：旅行青蛙基本是静态插画加少量动画，而路途的主画面是持续动画的横向场景。所以要在「手绘感」和「可程序化组合」之间找平衡：角色与地标手绘，天空、云、雨雪、远山由程序生成，但统一套用同一套手绘质感（纸纹、粗线条、有限色板）。第一步应产出一页风格指南。

## 2. 主场景系统（这个 App 的「魔法时刻」）

### 2.1 分层视差结构（从后到前）

1. 天空层：颜色由太阳高度角决定（黎明、金色时刻、白天、黄昏、蓝调时刻、夜晚）。日出日落用用户经纬度本地计算，不需要 API。
2. 天体层：太阳与月亮位置、真实月相、夜晚星空。
3. 远景层：远山、海平线、城市天际线，按当前地形类型选择（海岸、平原、山地、沙漠、森林、城市、乡村、河湖、极地）。
4. 中景层：地标与特色建筑（手绘单件）、植被（按季节与纬度变化：春樱、秋枫、冬雪）。
5. 路面层：旅人走的路，循环滚动。
6. 角色层：旅人及同伴。
7. 前景层：草丛、栏杆、飘过的落叶或雪花，制造纵深。
8. 天气层：雨、雪、雾、云影、闪电、风（表现为树和围巾的摆动）。
9. 氛围层：夜晚的路灯、窗户灯光、雨天地面反光。这些小细节是治愈感的主要来源。

### 2.2 现实数据到场景状态的映射

把所有输入先汇总成一个纯数据的 WorldState，再由 SceneDirector（纯函数）翻译成 RenderState。渲染层不关心数据从哪来，也方便做「演示模式」（手动拨时间和天气来调试，以及截图宣传）。

- 时间：设备时间与时区，推出太阳高度角与天空色板；季节按半球判断。
- 天气：API 的天气码映射到有限的场景天气状态（晴、少云、阴、小雨、大雨、雷雨、小雪、大雪、雾霾、大风）；温度决定角色穿着与呼出的白气；风速决定摆动幅度；AQI 决定雾霾层（国内用户很有感）；云量决定云层密度。
- 位置：城市级粗略定位即可，用于天气查询、时区、日出日落、出发地与「家」。不需要也不应上传精确坐标。
- 旅途进度：当前路段、距下一地标的距离、途经地形类型。
- 角色：当前角色与装扮；状态机输入（下雨撑伞、夜晚提灯、到达地标停下张望）。

### 2.3 降级策略

没有定位权限：让用户手选城市，或用 IP 粗定位。没有网络：用缓存天气，超时后退化为「只同步时间」，画面依然成立。天气 API 故障：同上。所有同步都是锦上添花，核心画面离线也能看。

## 3. 世界与路线

### 3.1 数据模型

世界是一张图：节点是地点（城市、地标、自然景观、小村子），边是路段（带地形类型、真实距离、沿途风物）。旅人沿边行走，进度以「旅途公里」计。

### 3.2 距离缩放

真实距离太大（北京到上海约 1200 公里），需要一个缩放比例，使得平均每 1 到 3 天到达一个新地点。时间驱动下可设定旅人每天走固定旅途公里，步数加速按比例折算。该参数在原型期调。

### 3.3 路线设计

首期做一条精心设计的主线即可，例如「从你的城市出发，走向海」，或主题路线：环中国、318 川藏线、丝绸之路、欧洲铁路线、环太平洋线。由用户选路线而不是让旅人随机乱走，内容才可控。地点数据可从 Wikidata、OpenStreetMap 导出初稿，再人工挑选首批 100 到 200 个地点。

### 3.4 每个地点的内容

一张手绘明信片（旅行青蛙最打动人的部分）、一段以旅人口吻写的短日记、一两条当地小知识或食物、可选环境音（海浪、集市、鸟鸣）。日记文本可用 LLM 批量生成初稿后人工审校，并带入当天真实天气和时间（「今天你那边下雨，我在成都也淋了一场，躲进了茶馆」）。

## 4. 角色系统

- 角色类型：背包客、骑行者、带狗的旅人、一只猫、小机器人、退休老人、带相机的摄影师等。每个角色有自己的文风，明信片语气不同；这才是选择角色的真正意义，而不只是换皮。
- 动画：骨骼动画加状态机。状态包括行走、停留张望、歇脚、避雨、夜晚睡觉或提灯夜行、到达地标庆祝、偶尔回头看镜头。输入来自 WorldState。
- 装扮：雨衣、围巾、帽子、同伴动物。一部分随天气自动出现（下雨自动撑伞），一部分由用户收集或购买。
- 工具：Rive（跨平台运行时，原生支持状态机，有免费档）为首选；Spine 更成熟但需付费；Lottie 适合 UI 小动画，不适合角色。

## 5. 陪伴感与减压设计

- 节律：早上「出发了」，晚上「今天走到了 X，晚安」。通知默认克制，频率由用户控制。
- 收藏与回忆：明信片收藏册、足迹地图（走过的路线点亮）、旅途日记时间线。这些是用户「回来」的理由，而不是打卡。
- 陪我走一段：用户出门散步时打开，旅人与你同步步伐，回来后收到一张「我们一起走过的路」。
- 专注模式（可选）：用户专注时旅人在走，不做惩罚（Forest 的枯树机制与减压定位相反）。
- 环境音：按真实天气播放对应环境音（雨声、风声、海浪），可独立当白噪音使用。
- 呼吸引导：与场景中的云、浪结合的一分钟呼吸。
- 桌面小组件、锁屏小组件、灵动岛：显示旅人当前所在地与天气，不打开 App 也在陪伴。高性价比功能。
- 轻社交（后期）：好友的旅人在路上相遇、互寄明信片。不做排行榜。
- 设计红线：无广告打断、无连续登录惩罚、无强制注册、无制造焦虑的文案。

## 6. 技术架构

### 6.1 跨平台方案选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Flutter + Rive + Flame / CustomPainter | 一套代码双端；UI 与自绘场景都强；Fragment shader 可做天空与天气；AI 编码工具对 Dart 支持好；全链路免费 | Dart 需要新学；Windows 上不能本地构建 iOS | 推荐 |
| React Native + react-native-skia + Rive | 若熟悉 JS/TS 上手快；Skia 也能自绘与 shader | 游戏循环与粒子不如 Flame 顺手；原生桥接偶有坑 | 备选 |
| Unity 2D | 动画与粒子最强 | 包体大；普通 App 的 UI、小组件、健康数据集成麻烦；对本项目过重 | 不推荐 |
| 原生（SwiftUI + SpriteKit / Compose） | 性能与系统感最好 | 两套代码，个人开发成本翻倍 | 不推荐 |

推荐 Flutter。主画面是「一个持续动画的自绘场景，周围是普通 App UI」，Flutter 的 CustomPainter / Flame 恰好擅长这种混合；Rive 有官方 Flutter 运行时；整条链路免费。主力机是 Windows，因此建议 Android 先行，iOS 构建走 Codemagic 或 GitHub Actions 的 macOS 跑道（均有免费额度），后期再考虑借或租一台 Mac。Codex CLI、Claude Code 写 Flutter 都很顺手。

### 6.2 分层架构

- 数据源层（Providers）：LocationProvider、ClockProvider（含日出日落、月相本地计算）、WeatherProvider（带缓存与降级）、StepsProvider（HealthKit / Health Connect）、JourneyRepository（本地 SQLite）。
- 状态层：WorldState（纯数据，可序列化）；SceneDirector（纯函数，WorldState 到 RenderState，可单元测试、可录制回放）。
- 渲染层：SceneView（Flame 或 CustomPainter 做分层视差与粒子）、Rive 角色、shader 做天空渐变、雨幕、雾。
- 应用层：明信片、地图、设置、角色选择等常规页面。
- 后端（MVP 可以没有）：内容 CDN（路线、地点、明信片资源按需下载，保持包体小）；天气代理（隐藏 API key、合并请求、缓存，省配额）；LLM 日记生成（服务端批量跑，不在客户端调用）；可选账号与云同步。免费起步可用 Supabase 或 Cloudflare Workers + R2；若主要面向国内用户，考虑腾讯云开发或阿里云的免费额度，国内访问更稳。

### 6.3 外部数据与 API

- 天气：Open-Meteo（非商业用途免费、无需 key、全球覆盖，起步首选）；和风天气（国内覆盖好、含 AQI，有免费开发者档）；彩云天气（分钟级降水）；Apple WeatherKit（iOS 原生，有免费额度）。缓存 30 到 60 分钟，按城市而非精确坐标请求。
- 日出日落、太阳高度角、月相：本地算法，无需网络。
- 步数：iOS HealthKit，Android Health Connect；国内部分手机厂商可能需要额外适配。
- 地点数据：Wikidata、OpenStreetMap、Natural Earth 做初稿，人工策展。

### 6.4 性能与电量

主场景常驻动画要注意电量：后台立即暂停；前台空闲时降到 30fps 或按需重绘；粒子数量封顶；雨雪用 shader 而不是成千上万个精灵；资源用图集。小组件用静态快照而非实时渲染。

### 6.5 内容生产管线

这是比代码更大的工作量，要当成一条独立流水线来建：

- 地点表（CSV / JSON）：名称、坐标、地形类型、所属路线、顺序、文案字段。
- 明信片插画：旅行青蛙风格的单张手绘。可先用 AI 生图出草稿定构图，再人工重绘统一风格；或委托一位插画师按风格指南批量产出。先写一页风格指南（线条粗细、色板、纸纹、留白规则），多人或多工具产出的图才能统一。
- 日记文案：LLM 生成，人工审校，模板变量（天气、时间、角色口吻）。
- 校验脚本：检查每个地点资源齐全、路线连通、距离合理。

## 7. 分期路线图

- 第 0 期，验证（2 到 4 周）：只做一个页面，天空加天气加一个走路的旅人，接真实时间和天气。不做路线、不做明信片。目标是验证「同一片天空」这个魔法时刻是否真的打动人：给几个朋友装上，看他们第二天会不会主动再打开。同期产出风格指南和第一个角色的 Rive 文件。
- 第 1 期，MVP（2 到 3 个月）：一条路线（约 30 到 50 个地点）、1 到 2 个角色、时间驱动加可选步数加速、明信片与足迹地图、纯本地、无账号、Android 先行。
- 第 2 期，陪伴深化：桌面小组件、环境音、专注模式、LLM 个性化日记、更多角色与路线、iOS 上架、云同步。
- 第 3 期，扩展：轻社交、季节活动、用户自定义路线（「帮我走一趟我的家乡」）、商业化。

## 8. 商业与合规

- 变现与产品气质一致：买断制或温和内购（角色、装扮、路线包、明信片包），不做广告，不卖进度。LLM 日记这类有持续成本的功能可放在小额订阅里。
- 隐私：定位只取粗略级别，在本地消费，隐私政策写清楚；健康数据按平台规则只用于功能本身。
- 国内上架：需要 App 备案（ICP），软著通常被各安卓商店要求，个人信息保护法合规。iOS 的定位与健康权限需要写清楚用途描述。

## 9. 主要风险

1. 内容量：几百个地点的插画是最大成本。缓解：程序化场景组合，只对重点地标手绘，明信片用卡片级插画。
2. 新鲜感衰减：没有压力机制的产品靠「持续有新东西」留人，内容节奏（1 到 3 天一个新地点）与小惊喜（旅人回头看你、特殊天气事件）要稳定供给。
3. 现实同步的脆弱性：权限拒绝、API 故障、国内网络环境，都要有体面的降级。
4. 电量与发热：常驻动画的硬约束。
5. 平台构建：Windows 上开发 iOS 的流程要尽早跑通，不要留到上架前。

## 10. 建议的下一步

1. 用一周做风格探索：参考旅行青蛙，画 3 张同一场景在不同时段与天气下的概念图，定色板与线条规则。
2. 决定前进机制（建议时间驱动加温和加速）与首条路线主题。
3. 搭 Flutter 工程，实现 WorldState 到 SceneDirector 到分层渲染的骨架，接 Open-Meteo 与本地日出日落算法，跑通第 0 期原型。
4. 准备地点表模板和明信片的内容格式。
