# Wanderling 模拟工作室设计评审 v1

2026-10-05 · @Yu Zhang

## 评审方法

结论先行：这轮评审把 Wanderling 从「一幅会动的风景」推向「一段有期待的关系」，新增 6 个入选设计点；需要拍板的 5 个决策已于 2026-10-05 全部定下，均采纳工作室推荐。

做法是模拟一家小型游戏工作室的立项评审（Greenlight），由 8 个角色 agent 轮流发言，每个角色只为自己的目标辩护：

| 角色 | 只关心 | 口头禅 |
| --- | --- | --- |
| 制作人 | 范围、节奏、能不能做完 | 「这个进 MVP 还是停车场？」 |
| 系统策划 | 核心循环、用户为什么回来 | 「第二天打开的理由是什么？」 |
| 叙事与内容策划 | 角色、文字、内容产量 | 「他为什么要走？」 |
| 美术总监 | 风格一致、资产成本 | 「这张图和锚点放在一起突兀吗？」 |
| 技术总监 | 网页优先路线下的可实现性、电量 | 「Safari 做得到吗？」 |
| 用户研究与健康设计 | 减压定位、不制造负罪感 | 「这会不会变成新的压力？」 |
| 增长与商业化 | 传播、留存、收入 | 「别人怎么知道有这个 App？」 |
| 红队（魔鬼代言人） | 找漏洞、反对共识 | 「如果这个假设是错的呢？」 |

流程按工作室常见的五步走：竞品拆解，各角色提案，交叉质询，可行性打分，收敛决策。评分的硬约束是我们的真实条件：一个不写代码的产品负责人加 Claude、网页优先（ADR-001）、AI 生图、先海外、阶段 1 到 2 零花费。

说明：本次会话没有联网搜索，竞品信息来自我已有的知识，细节可能过时，对外引用前请核实。

## 竞品拆解

最大的发现：没有一款产品同时做了「真实天空同步」和「替你远行」，这是 Wanderling 的空位；但每一半都有人做过，它们踩过的坑可以直接继承。

| 产品 | 核心机制 | 可借鉴 | 要避开 |
| --- | --- | --- | --- |
| 旅行青蛙（旅かえる） | 打包行囊后青蛙自己出门，几天后寄回照片 | 「看不见」制造期待；行囊是极轻的能动性；照片被大量截图传播 | 几乎没有长期目标，热度来得快去得快 |
| Finch | 完成自我照顾小事，小鸟成长并去冒险 | 宠物会反过来关心你；温和订阅制跑通了减压品类的商业化 | 打卡与连续天数会带来负罪感 |
| Neko Atsume | 摆好食物和玩具，猫不定时来访 | 静态场景加少量变体就够动人；照片簿是回来的理由 | 内容更新慢时留存下滑 |
| Alto's Odyssey 禅模式 | 无尽滑行，动态天气与昼夜 | 证明「分层视差加整体套色」的场景足以治愈 | 没有收藏和进度，只是一种模式 |
| Slowly | 笔友信件按真实距离延迟送达 | 延迟本身就是期待与浪漫，几乎不花开发成本 | 真人社交带来审核与安全成本 |
| Window Swap（网站） | 看世界各地陌生人的窗外 | 验证了「什么都不做，只是看」是真实需求 | 没有留存机制 |
| Lofi Girl 直播、Spirit City | 工作时作为背景陪伴 | 桌面「第二屏」是压力大的年轻人的高频场景 | 做成工具后失去角色感 |
| Walkr、Pikmin Bloom | 步数驱动探索 | 现实行为与虚拟进度绑定很有吸引力 | 久坐用户的负罪感 |
| Forest | 专注时树生长，中断则枯死 | 专注场景与压力人群高度重合 | 惩罚机制与减压定位相反 |
| Animal Crossing | 与现实时钟、季节、节日同步 | 现实日历就是免费的内容日程 | 内容量与系统复杂度远超我们 |
| (Not Boring) Weather、Carrot Weather | 有个性的天气 App | 看天气是每天已有的习惯，可以借力 | 工具属性太重会压过情感 |
| Kind Words | 向陌生人写温和的信 | 温柔的异步轻社交 | 需要人力或模型审核 |

三条可以直接继承的规律：期待比即时奖励更治愈（青蛙、Slowly）；极轻的能动性让用户觉得「是我的」（行囊、摆猫碗）；可截图的画面就是增长引擎。

## 第一轮：各角色提案

七个角色共提出 15 条提案（红队本轮不提案，只在第二轮质询）。编号供后文引用。

| 编号 | 提出者 | 提案 | 理由 |
| --- | --- | --- | --- |
| P1 | 制作人 | 桌面横屏「陪伴窗」：电脑浏览器全屏展示场景，隐藏界面 | 网页优先让这件事几乎免费；上班族白天对着电脑，比手机更长时间可见 |
| P2 | 制作人 | 一句话天气关心：旅人在信里提醒「明天你那边有雨，带伞」 | 借用用户每天看天气的既有习惯，给出实用的打开理由 |
| P3 | 系统策划 | 慢递明信片：到达地标后，明信片按「他到你」的距离延迟几小时到两天送达 | 把即时奖励变成期待；越远越慢，距离变得可感知 |
| P4 | 系统策划 | 行囊：用户可以（不必）给他放一件小东西，如一本书、一块饼干、一把伞 | 极轻的能动性；物品与地点组合出不同的日记和小事件 |
| P5 | 系统策划 | 路上的小事：两个地标之间随机出现小场景，如路边的狗、桥上的日落 | 填充 1 到 3 天的到达间隔，让每次打开可能不一样 |
| P6 | 叙事策划 | 上路的理由：每条路线有一个轻轻的动机（替你去看海）和一个终点（回家） | 没有长期目标是旅行青蛙热度消退的原因之一 |
| P7 | 叙事策划 | 主角是一个小生物，而不是具体的人 | Wanderling 的 -ling 本就指小东西；不涉及年龄性别种族，海外更通用，代码也更好画 |
| P8 | 叙事策划 | 他会问你：信末偶尔有一个问题，用户点一下选项回答，下一封信会提到 | 从「看他」变成「互相惦记」，是 Finch 最有效的一点 |
| P9 | 美术总监 | 场景用「地形套件」程序组合，只有明信片是单张生图 | 把美术量从「每个地点一套」降到「每种地形一套加每个地点一张」 |
| P10 | 美术总监、增长 | 明信片一键导出为 9:16 分享图，带邮戳、日期和两地天气 | 旅行青蛙靠截图传播；这是零营销预算下最便宜的增长 |
| P11 | 技术总监 | 真实天象事件：满月、流星雨、至日、日月食在场景里自动发生 | 本地计算加一张静态日历即可；「同一片天空」最有说服力的时刻 |
| P12 | 技术总监 | MVP 不做推送，用 App 内「信箱」承接所有来信 | iOS 网页推送需要添加到主屏幕和服务端，先省掉 |
| P13 | 用户研究 | 首次打开的「看看窗外」：定位后提示用户抬头对比真实天空 | 把魔法时刻放在第一分钟，而不是等用户自己发现 |
| P14 | 用户研究 | 文案红线规范：禁用「你错过了」「好久不见」「连续 X 天」等句式 | 让减压定位可以被检查，而不只是愿望 |
| P15 | 增长与商业化 | 网页版永久免费，原生版卖路线包与角色 | 网页是拉新漏斗，支付放在 App Store 阶段，避开网页支付的麻烦 |

## 第二轮：交叉质询

七场争论里，最关键的是第一场：红队指出「永远看得见」会削弱期待，这改变了信息节奏的设计。每场给出双方观点和制作人的裁决。

### 1. 永远可见，还是留一点看不见

- 红队：旅行青蛙的魔力来自青蛙出门后你看不见他。我们天天能看见他走路，第三周就是壁纸。
- 系统策划：场景负责「同一片天空」的陪伴，期待交给慢递明信片（P3）和路上的小事（P5）。
- 裁决：画面永远在，但信息分批给。他在哪里随时知道，他看到了什么要等信。地标在场景里只是远远的剪影，完整的样子只在明信片上。

### 2. 零操作，还是给一点能动性

- 用户研究：行囊（P4）一旦会「用完」，就变成每日任务。
- 系统策划：不放东西他照样走，放了只是多一点故事。
- 裁决：行囊只有一格，物品不消耗，放一次可以陪他走好几天；没有「行囊空了」的提醒。

### 3. 游戏，还是会讲故事的天气 App

- 制作人：看天气是每天都有的习惯，做成天气 App 留存最稳。
- 叙事策划：一旦出现温度曲线和降水概率，它就是工具，不再是一个人。
- 裁决：不做天气面板。只取 P2 的「一句话关心」，由旅人说出口；想看温度，点一下天空显示一个数字即可。

### 4. 旅人是人，还是小生物

- 美术总监：小生物形状简单，代码绘制更稳，风格也更统一。
- 增长：人类背包客更容易让用户代入「替我去看」。
- 红队：反过来说，人类角色会被问「他多大、哪里人、为什么不上班」。
- 裁决：倾向小生物，留给 Yu 拍板（见决策 D1）。

### 5. 信里写不写他那边的真实天气

- 红队：用户在伦敦晴天，信里写冰岛在下雪，是不是破坏了「天空归现实」？
- 用户研究：场景天空始终是用户的，信里的对比反而让距离可感知：「你那边放晴，我这边在下雪」。
- 裁决：采纳。成本只是多查一次 Open-Meteo，且只在写信时查。

### 6. 内容够不够用

- 红队：40 个地点、平均 2 天一个，约 80 天就走完，之后呢？
- 制作人：走完就「回家」，这是一个完整的故事；第二条路线在上架后做，也是付费点。
- 裁决：首条路线按约 3 个月设计，地点之间用 P5 的小事和 P11 的天象填充，就不需要更多地点。

### 7. 没有推送，留存会不会崩

- 增长：慢递明信片没有通知，用户不知道有信。
- 技术总监：iOS 网页推送要服务端和主屏幕安装；原生版的本地通知不需要服务器。
- 裁决：MVP 不推送，用 M1 朋友测试里「第二天会不会再打开」来检验；上架原生版时加每日最多一条的本地通知。

## 第三轮：可行性评审

6 个提案落在「价值高、成本低」，应先做；P4、P5、P8、P9 价值高但要投入真工作量，排进 MVP 史诗。

价值看是否服务四个支柱、能否提升「第二天再打开」；成本按我们的条件估：网页优先、一人加 Claude、AI 生图、零预算。P12 不推送与 P15 商业模式是决策而非功能，不参与打分。

## 收敛：支柱、循环与 MVP 调整

Wanderling 的答案从「一个会动的风景」变为「一个在路上给你写信的小旅人」：场景负责此刻，信件负责期待。

### 五个产品支柱

1. 同一片天空：天空、天气、天象与你的现实同步。
2. 他在路上：画面一直在，故事要等信。
3. 什么都不用做：可以参与，不参与也不会失去任何东西。
4. 小而可收藏：每张明信片都是能拿给别人看的一件小东西。
5. 总有一点意外：每次打开都可能遇见点什么，错过也不会失去。（第四轮新增，2026-10-05 采纳）

每个新功能都要能指出它服务哪个支柱；违反第 3 条的直接否决。

### 核心循环（按时间尺度）

| 时间尺度 | 用户做什么 | 得到什么 |
| --- | --- | --- |
| 每次打开，约 10 秒 | 看一眼 | 和窗外一样的天空，一个仍在走的他 |
| 每天 | 开信箱，可选放行囊 | 路上的小事、一句天气关心 |
| 每 1 到 3 天 | 收明信片，可选分享 | 一个新地点、两地天气的对照 |
| 每月 | 什么也不用做 | 满月、流星雨、季节变化 |
| 每条路线，约 3 个月 | 陪他走完 | 回家，足迹地图完整，一本明信片册 |

### 对开发规划的具体改动

| 提案 | 去向 | 影响 |
| --- | --- | --- |
| P13 看看窗外、P1 桌面陪伴窗 | 阶段 1 第 5 周 | 都很便宜，而且直接影响 M1 朋友测试的结果 |
| P14 文案红线 | 立即 | 写进风格指南，所有文案入库前检查 |
| P9 地形套件 | 阶段 1 起 | 美术管线改为「每种地形一套加每个地点一张明信片」 |
| P3 慢递、P10 分享图 | MVP 史诗 D | 明信片从到达即得改为延迟送达 |
| P2 天气关心、两地天气、P5 小事 | MVP 史诗 B | 信件模板增加变量；小事首批 20 到 30 条 |
| P4 行囊 | MVP 史诗 A | 一格、不消耗、无提醒 |
| P11 天象 | MVP | 满月、流星雨、至日进 MVP；日月食进停车场 |
| P8 他会问你 | MVP 末尾 | 时间紧就移到上架后 |
| P12 不推送 | 确认 | 本地通知随原生版上线 |

## 第四轮：惊喜、彩蛋与独特玩法

结论：Wanderling 最独特的彩蛋来源是「现实本身」。别的游戏的彩蛋藏在关卡里，我们的藏在你窗外的天气、月亮和日历里，这是竞品都没有的，而且大多只需本地计算。

制作人先定一条规则：粘性来自「打开可能遇见点什么」，绝不来自「不打开就会失去」。为此所有彩蛋错过了都不会消失，而是变成一封信：「昨天雨后有彩虹，你看到了吗？」

### 现实触发的彩蛋

| 彩蛋 | 触发条件 | 发生什么 | 频率 | 成本 |
| --- | --- | --- | --- | --- |
| 雨后彩虹 | 你那边雨刚停、太阳偏低、有云缝 | 场景里出现彩虹，他转身指给你看，轻轻提示「看看窗外」 | 稀有 | 低 |
| 两地同雨 | 你那边和他那边同时下雨 | 一张特别的明信片：两把伞 | 稀有 | 低 |
| 今冬初雪 | 你所在城市当季第一场雪 | 他停下堆一个很小的雪人，雪人留在路边几天 | 每年一次 | 低 |
| 流星雨之夜 | 真实流星雨极大之夜，夜间打开 | 有机会看到流星并许愿，愿望封存一年后寄回给你 | 每年几次 | 中 |
| 满月 | 真实满月 | 他坐下赏月，信里有一句关于月亮的话 | 每月 | 低 |
| 新年零点 | 你当地跨年时打开 | 他点一支很小的烟花 | 每年一次 | 低 |
| 日出那几分钟 | 你当地日出前后 5 分钟内打开 | 他对着太阳伸懒腰，得到一枚「早起的人」邮戳 | 少见 | 低 |
| 深夜两点到四点 | 凌晨打开 | 他睡着了，一只萤火虫替他说「嘘，你也早点睡」 | 少见 | 低 |
| 你的生日 | 用户可选填写生日 | 当天收到一张从最远处寄来的明信片 | 每年一次 | 低 |
| 路过你的城市 | 主线经过你所在城市附近 | 他特意绕路，寄来「我经过你家了」 | 极稀有 | 中 |

### 藏在触摸里的彩蛋

| 动作 | 发生什么 | 成本 |
| --- | --- | --- |
| 摇一摇手机 | 下雪时整个画面变成雪花球；秋天落叶纷纷飘下 | 中：iOS 网页需请求动作权限 |
| 长按旅人 | 他回头向你挥手 | 低 |
| 连续点他很多下 | 他坐下假装生气，然后递给你一颗糖 | 低 |
| 夜里在星空上连线 | 你画的「星座」会在下一封信里被他起名字 | 中 |
| 点月亮 | 显示今天真实的月相名字 | 低 |
| 把手机横过来 | 他停下拿出相机，进入拍照模式 | 低 |

### 路上的奇遇（低概率随机）

一只跟了他三天的猫，可能离开，也可能留下成为同伴；另一个 Wanderling 擦肩而过；捡到一封不知道写给谁的信；海岸线上远处的鲸鱼；极地的极光；沙漠里的海市蜃楼。这些和 P5「路上的小事」共用一套引擎，只是更稀有。

### 五个竞品没有的玩法

| 玩法 | 怎么玩 | 为什么独特 | 阶段 |
| --- | --- | --- | --- |
| 天空交换 | 拍一张你窗外的天空，只在本地提取颜色；他下一张明信片用你天空的颜色上色，信里写「原来你那边的云是这个颜色」 | 第一次让用户的现实反过来改变他的世界；照片不上传 | MVP |
| 流星愿望胶囊 | 真实流星雨夜许愿，封存一年，到期他把愿望寄回来，问你实现了没有 | 把天文日历变成一年后的约定 | MVP |
| 慢信回寄 | 你给他写一句话，按距离几天后才到他手里，他的回信会提到 | 双向的慢通信，不是聊天机器人 | 上架后，需 LLM |
| 共此时邮戳 | 全世界同一时刻看到同一次满月或流星雨的用户，匿名得到同一枚邮戳和一个数字：「此刻有这么多人和你看着同一个月亮」 | 没有好友、没有聊天的社交，恰好是「同一片天空」的最强表达 | 上架后，需要一个很小的计数后端 |
| 我们的一年 | 年底生成一张长图：他走了多远、你们一起淋过几场雨、看过几次满月 | 记录的是你的真实天空，而不是使用时长；年底天然的传播窗口 | MVP 之后的第一个年底 |

### 惊喜引擎（技术总监）

所有彩蛋写成数据规则：触发条件、概率、冷却时间、是否一次性、错过后的信件文案，由 SceneDirector 对照 WorldState 判断。这样新增彩蛋是填表而不是写代码：Claude 批量起草，Yu 审核。演示模式要能强制触发任何一个彩蛋，方便测试和截宣传图。

### 红队的三条约束

- 彩蛋太密就不是彩蛋。每天最多一个「大」惊喜，稀有的就真的稀有。
- 彩蛋不写攻略。让用户互相告诉「你知道摇一摇会怎样吗」，口口相传本身就是传播。
- 爆款无法被设计，能设计的是「值得截图」和「值得说给别人听」。M1 朋友测试增加一个指标：有没有人主动截图发给别人。

### 调整与新增决策

- 新增第五个支柱「总有一点意外」（2026-10-05 已采纳，见五个产品支柱）：每次打开都可能遇见点什么，错过也不会失去。
- 进 M1 原型的 5 个彩蛋（最便宜、最能验证魔法时刻）：雨后彩虹、满月赏月、深夜睡着、长按挥手、摇一摇雪花球。
- D5（已定，采纳推荐）：惊喜图鉴显示未发现的剪影和诗意提示（如「某个下雪的满月夜」），用来勾起探索欲；永不显示完成百分比，避免收集压力。

## 决策结果（已拍板）

Yu 于 2026-10-05 拍板，五个决策全部采纳工作室推荐。最急的 D1 定为小生物，阶段 1 第 4 周按此画旅人。

| 编号 | 决策 | 结论（采纳工作室推荐） | 最晚何时定 |
| --- | --- | --- | --- |
| D1 | 旅人是人，还是小生物 | 小生物：圆润、背包、不涉及年龄性别，与 Wanderling 的名字呼应 | 阶段 1 第 4 周开工前 |
| D2 | 首条路线如何兼顾「从你家出发」与全球用户 | 第一段「出门」是程序生成的通用场景，几天后他搭上一条船或一班火车，进入策划好的主线 | MVP 史诗 A 开工前 |
| D3 | 是否把第二个角色推迟到上架后 | 是，把容量让给慢递、行囊、小事 | MVP 开工前 |
| D4 | 商业模式 | 网页版免费，原生版卖路线包；不做广告，不卖进度 | 阶段 3 开工前 |
| D5 | 惊喜图鉴是否显示未发现的剪影和诗意提示 | 显示剪影和诗意提示，永不显示完成百分比 | 做惊喜图鉴之前 |

D2 的背景：红队指出，先海外意味着用户可能在任何城市，而策划好的地点只能覆盖一条线。「搭船或火车」是把任意起点接到固定主线的叙事接口。

## 可复用的 agent 角色卡

以后每个史诗开工前开一次「迷你评审」：选 3 个相关角色加红队，各发言一轮、质询一轮、制作人裁决。下面的角色卡可以放进仓库的 `.claude/agents/`，在 Claude Code 会话里作为子 agent 召集。

| 角色 | 任务与立场 | 必问的问题 | 何时召集 |
| --- | --- | --- | --- |
| 制作人 | 守范围与节奏，最后裁决 | 它服务哪个支柱？进 MVP 要拿什么换？ | 每次评审 |
| 系统策划 | 设计循环与节奏 | 第二天、第二周、第二个月打开的理由分别是什么？ | 旅途引擎、信件、行囊 |
| 叙事与内容策划 | 角色口吻与内容产量 | 这句话像他说的吗？每周要生产多少条？ | 路线、文案、小事 |
| 美术总监 | 守风格指南与资产成本 | 和锚点放在一起突兀吗？能不能程序化？ | 任何新资产 |
| 技术总监 | 守网页路线与电量 | iPhone Safari 做得到吗？离线和权限被拒时怎么降级？ | 每次评审 |
| 用户研究与健康设计 | 守减压定位与文案红线 | 三天不打开的用户回来时会感到什么？ | 任何带提醒、数字或收集的功能 |
| 增长与商业化 | 传播、留存、收入 | 用户会把什么截图发给朋友？ | 分享、上架、定价 |
| 红队 | 反对共识，找最弱的假设 | 如果这个假设是错的，我们何时会发现？ | 每次评审 |

共同规则：每个角色发言不超过 3 点；必须引用已确认的约束（ADR-001、风格指南、四个支柱）；评审结论写进开发日志或决策记录。
